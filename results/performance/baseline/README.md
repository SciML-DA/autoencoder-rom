# performance baseline

Reference timings for the **unoptimised** models, taken before any perf work.
Every later optimisation is measured against this.

Measured on 3x NVIDIA T4 (meteor), one config per GPU, 192 configs, ~9.5 min.
Generated by `perf/baseline.slr` -> `perf/baseline.py --merge` -> `perf/plots.py`.

`results.csv` — one row per (dataset, model, latent, width variant). `s_per_epoch`
is steady state: each config gets a throwaway warmup fit first, so XLA JIT and
cuDNN autotune land in `compile_s` instead of being smeared into the per-epoch
figure.

| Figure | What it shows |
|---|---|
| `time_vs_params.png` | Cost vs parameter count. Dense AE is flat then near-linear, knee at 7.2e6 params. Conv spread is architecture, not noise. |
| `time_vs_latent.png` | Cost vs latent. The flat `fixed_sm`/`fixed_lg` lines are the point: at fixed width, latent is free. |

| `jax_ratio.png` | Where JAX wins and loses. `circle` conv sits at ~0.25 — JAX 4x slower there. |

## The two results that matter

**Latent size is nearly free; width is what costs.** Holding width fixed, a
128x increase in latent (2 -> 256) changes runtime by <=3%. The default
`SCALED_HIDDEN = (8k, 2k)` ties width to latent, which is why the study's own
sweep looks latent-driven. It isn't.

**Below ~7e6 parameters nothing is compute-bound.** Slopes are 0.02 (AE) and
0.00 (AEJax) under the knee, 0.70 and 0.78 above it. `CAE` is flat throughout
(slope 0.01, R^2 0.01) — parameter count does not predict its cost at all;
grid size and step count do.

## Caveats

- `peak_mem_mb` is meaningless for the JAX rows: `torch.cuda.max_memory_allocated`
  only sees torch's allocator, and JAX preallocates its own pool. Torch rows are
  real (AE@256 on circle peaks at 3.3 GB).
- The largest `compile_s` values, mostly at k=2, are the first config in each
  process and absorb one-off XLA/CUDA init rather than per-config compilation.
  Medians are the honest figure.
- 15-epoch steady-state measurements. Early stopping means real runs are shorter.
